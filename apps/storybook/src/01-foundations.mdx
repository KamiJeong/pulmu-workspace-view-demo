# Pulmu Design System Foundations

Pulmu Design System v0.1이 제품 상태를 일관되게 설명하고, 이후의 화면과 컴포넌트가 같은 의미를 공유하도록 하는 기반 문서다. `$pulmu`는 사용자가 호출하는 하나의 공개 명령이며, 아래 단계는 그 안에서 Orchestrator가 진행하는 하나의 forge workflow다.

<h2 id="principles" tabIndex={-1}>원칙과 정보 계층</h2>

1. **Workflow truth:** 화면은 Pulmu의 기존 workflow 계약을 표현하며 새 동작을 만들지 않는다.
2. **One command, seven stages:** 사용자는 `$pulmu` 하나를 시작하고, Orchestrator가 일곱 단계를 전환한다.
3. **Meaning before decoration:** 단계, lifecycle, 역할, 위험과 전달 상태의 의미를 색이나 장식보다 먼저 전달한다.
4. **Safe observability:** UI는 raw Run Context를 직접 렌더링하지 않고 allowlist adapter가 만든 UI model만 소비한다.
5. **Accessible by default:** 키보드, 보조 기술, 확대, reflow, forced colors와 reduced motion을 기본 조건으로 다룬다.

정보는 **run 요약 → 현재 stage → 전체 timeline → 검증·검토·delivery → 세부 메타데이터** 순으로 읽히게 한다. 상태는 아이콘, 텍스트 label과 구조를 함께 사용하며 색만으로 구분하지 않는다.

<h2 id="lifecycles" tabIndex={-1}>Run lifecycle과 stage lifecycle</h2>

둘은 서로 다른 축이며 retry는 별도의 run status가 아니다.

- **Run lifecycle:** <code>{PULMU_RUN_STATUSES.join(", ")}</code>
- **Stage lifecycle:** <code>{PULMU_STAGE_STATUSES.join(", ")}</code>
- `running` run은 정확히 하나의 현재 stage가 `in_progress`다.
- `completed` run은 Ship까지 완료된 상태다. `failed`와 `interrupted`는 멈춘 위치를 보존한다.
- retry 중인 run은 계속 `running`이며, retry counter와 되돌아간 현재 stage를 함께 보여 준다.

<h2 id="roles" tabIndex={-1}>역할과 one-writer model</h2>

Orchestrator는 workflow를 제어하고, **Smith (`pulmu_smith`)만 application/source/test file을 쓴다.** 나머지 agent는 모두 read-only이며 조사, 설계, 분석 또는 검토 결과만 반환한다.

<ul>
  {PULMU_AGENTS.map((agent) => (
    <li key={agent.name}><code>{agent.name}</code> — {agent.role}; <strong>{agent.access}</strong></li>
  ))}
</ul>

동시에 수행해도 안전한 read-only 작업만 병렬화한다. Quench나 Hone에서 수정이 필요하면 같은 Smith를 다시 사용해 one-writer 경계를 유지한다.

<h2 id="retries-delivery" tabIndex={-1}>Retry와 delivery</h2>

- **Quench retry:** 최대 {PULMU_RETRY_POLICIES.quench.maxRetries}회, <code>{PULMU_RETRY_POLICIES.quench.path.join(" → ")}</code>. 실패 원인을 수정한 뒤 반드시 다시 검증한다.
- **Hone refinement:** 최대 {PULMU_RETRY_POLICIES.hone.maxRetries}회, <code>{PULMU_RETRY_POLICIES.hone.path.join(" → ")}</code>. medium/high finding은 Smith 수정과 재검증·재검토를 거친다.
- **Local delivery:** 검증·검토된 local commit이 생성되면 완료된다. PR이 없어도 정상 완료다.
- **GitHub delivery:** commit과 일반 push 뒤 실제 pull request URL을 얻어야 완료된다. force-push와 auto-merge는 하지 않는다.
- 실행 중에는 delivery가 `pending / unknown`, 실패·중단 시에는 `not delivered`다. 완료된 Run Context에 PR이 없으면 local, 유효한 PR이 있으면 GitHub delivery로 해석한다.

<h2 id="experience-rules" tabIndex={-1}>경험 품질 기준</h2>

### Accessibility

WCAG 2.2 AA를 **목표**로 하며 conformance를 선제적으로 주장하지 않는다. semantic heading, list, description list와 필요한 경우 caption이 있는 table을 사용한다. 모든 동작은 키보드로 가능해야 하고 visible focus를 유지한다. 텍스트·비텍스트 contrast, screen-reader reading order, forced-colors mode와 Storybook a11y 결과를 확인한다. 상태와 위험은 색만으로 전달하지 않는다.

### Responsive와 reflow

기본 reading order는 하나이며 320px와 390px에서 single column을 유지한다. 페이지 전체에 가로 scroll을 만들지 않고 긴 stage·branch·area label은 안전하게 줄바꿈한다. table과 code가 꼭 필요할 때만 해당 영역 안에서 scroll을 허용한다. 320px 너비에서 400% reflow와 200% text zoom에서도 내용이나 focus가 잘리지 않아야 한다.

### Theme과 motion

Storybook toolbar의 기본 선택은 `System`이며 OS의 `prefers-color-scheme`을 실시간으로 따른다. `Light` 또는 `Dark`를 고르면 그 사용자 선택을 저장하고 OS 변경과 분리한다. 상세 값과 contrast 근거는 `02 Tokens` catalog를 따른다. Theme 전환은 색만 바꾸고 focus, viewport, locale, controls와 story state를 유지한다. forced colors에서도 같은 정보 계층을 유지하고, 필수 정보를 animation에 의존하지 않으며 `prefers-reduced-motion: reduce` 또는 Storybook motion suppression 설정에서는 비필수 transition과 animation을 제거한다.

### Content와 internationalization

한국어를 우선하되 canonical English term은 처음 등장할 때 함께 쓴다. 한국어 content root에는 `lang="ko"`를 지정한다. UI string은 외부화할 수 있는 완결된 문장으로 작성하고 단어 조각을 이어 붙이지 않는다. 임의의 대문자 변환을 피하고 날짜·시간·숫자는 locale-aware formatter를 사용한다. 번역이 길어져도 label과 layout이 줄바꿈돼야 한다. 오류는 원인, 영향과 다음 행동을 간결하게 설명하며 raw command output을 그대로 노출하지 않는다.

### Data safety와 adapter boundary

예시는 synthetic·anonymized data만 사용한다. UI는 raw Run Context v1을 `@pulmu/model`의 allowlist adapter로 변환한 결과만 렌더링한다. Adapter는 schema, lifecycle, stage, retry와 terminal invariant를 검증하고 timeline과 delivery 상태를 파생한다.

다음 값은 UI model로 복사하지 않는다: task prompt, error message, credential, 사람 이름·email, local path, repository·branch·run identifier, environment value, raw log·command output, model response, PR URL과 알 수 없는 field. 안전하지 않은 raw context는 화면에 부분 렌더링하지 않고 명시적인 invalid-data state로 처리한다.

<h2 id="theme-runtime" tabIndex={-1}>Theme runtime과 future app 적용</h2>

Storybook의 theme preference 계약은 `system | light | dark`, 실제 root에 적용되는 resolved theme은 `light | dark`다. 저장 key는 <code>pulmu.theme.preference.v1</code>이며 저장하는 값은 resolved color가 아니라 사용자가 고른 preference다. 값이 없거나 올바르지 않고 storage 접근이 실패하면 `system`으로 안전하게 돌아간다.

향후 app은 다음 순서로 같은 계약을 적용한다.

1. 첫 visible content와 stylesheet 평가 전에 head의 작은 inline bootstrap에서 저장된 preference를 읽는다.
2. `system`이면 `prefers-color-scheme: dark`를 해석하고, root의 `data-theme`과 `style.colorScheme`을 같은 resolved 값으로 함께 설정한다.
3. app hydration 뒤 runtime controller를 연결한다. OS change listener는 `system`일 때만 유지하고 manual preference에서는 해제한다.
4. 사용자 선택만 stable key에 저장한다. route나 screen이 임시로 지정한 effective override는 저장하지 않는다.
5. Theme 변경을 위해 remount, reload 또는 transition을 추가하지 않으며 focus, locale, motion, viewport와 component state를 건드리지 않는다.

Storybook 구현은 이 순서를 Canvas와 Docs에 공통 적용한다. App으로 옮길 때도 token package나 component API를 바꾸지 말고 bootstrap과 controller boundary만 framework entry에 연결한다.

<h2 id="browser-baseline" tabIndex={-1}>지원 브라우저 기준</h2>

현재 안정 버전과 바로 이전 버전의 Chrome, Edge, Firefox, Safari를 지원 기준으로 삼고 Storybook 자동 검증은 Chromium을 기준으로 한다. JavaScript, CSS custom property와 modern layout을 사용할 수 없는 Internet Explorer 및 legacy embedded WebView는 지원하지 않는다. 브라우저별 차이가 정보 접근이나 keyboard 사용을 막지 않는지 실제 browser에서 확인한다.

<h2 id="non-goals" tabIndex={-1}>v0.1 non-goals와 지원하지 않는 개념</h2>

v0.1은 다음을 제공하거나 암시하지 않는다.

- 완성된 light/high-contrast theme, 전체 시각 component library 또는 brand redesign
- live Run Context polling, raw command output·log viewer, terminal emulator
- 기존 Pulmu workflow 동작, stage 순서, agent routing, retry 또는 delivery 정책 변경
- hosted multi-tenant SaaS, cloud synchronization 또는 원격 실행 제어
- user account, organization/team membership, invite, RBAC/SSO, billing/subscription, usage quota
- 알림 센터, 감사 log, 장기 analytics나 run history 제품 정책

이 개념이 향후 필요해지면 별도 product contract, 개인정보·보안 검토와 접근성 기준을 먼저 정의한다.
